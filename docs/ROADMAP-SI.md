# 개선 로드맵 — SI 현장 PLC·상위 PC 개발자 대상

> 목표 사용자: 로봇 시스템 통합(SI) 현장에서 **로봇 입고 전, 또는 로봇 없이** PLC 인터록·핸드셰이크 로직과 상위 PC(MES·비전·HMI) 통신 프로그램을 개발·시험하는 엔지니어.
>
> 판단 기준: **"에뮬레이터에서 통과한 PLC·PC 프로그램이 실제 로봇에서도 수정 없이 동작하는가."** 3D 표현이나 궤적 정밀도보다 신호·통신·상태 전이의 현실성을 우선합니다.

## 1. 현재 상태 요약

**강점 (유지)**

- 5개 제조사 통신 프로토콜 + Modbus TCP + OPC UA 를 하나의 프로그램에서 동시에 제공
- 5개 제조사 로봇 언어 실행 → 로봇 프로그램과 PLC 로직을 함께 시험 가능
- 신호 타임라인, 사이클 타임, 셀 주변기기 연동, 배속
- 무료, 브라우저 기반, OS 무관 설치

**핵심 갭 (코드 확인 결과)**

| 갭 | 근거 | PLC 개발에 미치는 영향 |
|---|---|---|
| 운전 모드 인터록 없음 | `controller.start()` 는 알람·서보만 확인. 모든 프로토콜이 모드와 무관하게 시작 명령 수락 | TEACH 모드에서 외부 시작이 거부되는 실제 동작을 시험할 수 없음 → 현장에서 "왜 시작이 안 되지" 문제 발생 |
| 전용 시스템 I/O 없음 | 범용 DI/DO 512점만 존재, 외부 시작·프로그램 번호 선택 등 고정 신호 없음 | SI 현장의 대표적인 PLC↔로봇 인터페이스(하드와이어/필드버스 시스템 신호)를 그대로 시험할 수 없음 |
| 안전 신호·정지 범주 없음 | 비상정지·안전 펜스·인에이블 관련 코드 없음 | 비상정지 후 복귀 시퀀스, 펜스 개방 처리 같은 필수 PLC 로직을 시험할 수 없음 |
| 통신 트래픽을 볼 수 없음 | `protocols/common.js` 로그는 같은 메시지를 3초에 1회로 억제, 요청·응답 원문 없음 | 연동 오류 원인(주소·엔디언·형식)을 찾기 어려움. 와이어샤크를 따로 써야 함 |
| 프로토콜 검증 수준 미공개 | README 에 "원문과 대조하지 못한 부분" 명시 (Hyundai 경로, Yaskawa 부가 상태 코드) | 사용자가 어디까지 믿어도 되는지 알 수 없음 |
| 고장 주입 수단 없음 | 통신 지연·끊김, 그리퍼 실패, 센서 고장 등을 일부러 만들 방법 없음 | PLC 코드의 대부분을 차지하는 예외 처리 경로를 시험할 수 없음 |
| 시험 자동화 수단 부족 | REST `/api/cmd` 는 있으나 시나리오 실행·판정·리포트 기능 없음 | 회귀 시험을 손으로 반복해야 함 |
| 필드버스 제한 | Modbus TCP, OPC UA 만 지원 | 실제 로봇은 PROFINET·EtherNet/IP·CC-Link 가 주류 → PLC 측 통신 설정·I/O 맵을 그대로 시험할 수 없음 |

## 2. 개선 항목

규모: **S** ≈ 1주 이하, **M** ≈ 2~4주, **L** ≈ 1~2개월 (1인 기준 대략).

### P0 — 시험 결과의 신뢰도 (이것 없이는 "에뮬레이터에서 됐는데 현장에서 안 됨"이 반복됨)

#### P0-1. 운전 모드 인터록 · 외부 운전 조건 — S ✅ 1단계 완료

- **내용**
  - 제조사별 외부(원격) 시작 허용 조건을 구현: 예) REMOTE 모드 + 서보 ON + 알람 없음 + 프로그램 선택됨.
  - 조건 불충족 시 각 프로토콜이 **실제 컨트롤러와 같은 방식으로 거부** (Yaskawa HSE 상태 코드, RWS HTTP 오류, KUKA `$PRO_STATE` 등).
  - 모드 전환 시 실행 중 프로그램 정지(실제 동작과 동일).
  - UI 의 시작 버튼은 TEACH/PLAY 에서 허용(펜던트 조작에 해당), 외부 명령은 REMOTE 에서만 허용. 시험 편의를 위한 `인터록 무시` 옵션 제공.
- **완료 기준**: 모드별 × 인터페이스별 시작 허용/거부 매트릭스 테스트 통과, 거부 사유가 로그와 상태 레지스터에 표시.

#### P0-2. 제조사별 전용 시스템 I/O 프리셋 — M ✅ 1단계 완료

- **내용**: 제조사 관례에 맞춘 시스템 신호를 DI/DO 에 할당하는 프리셋 (번호는 프리셋에서 바꿀 수 있게).

  | 구분 | 신호 예 |
  |---|---|
  | 입력 (PLC → 로봇) | 외부 서보 ON, 외부 시작, 외부 홀드, 외부 정지, 알람 리셋, 프로그램 번호(PGNO, 4~8 bit) + 스트로브(+패리티), 원점 복귀 |
  | 출력 (로봇 → PLC) | 운전 중, 서보 ON, 알람, 홀드 중, 원점 위치, 프로그램 번호 응답(PGNO 확인), 사이클 완료, 리모트 모드 |

  - 프리셋: Yaskawa 전용 입출력, ABB System I/O, KUKA Automatic External(`$EXT_START`, `PGNO_TYPE`, `$PGNO_REQ` 등), Kawasaki 전용 신호, Hyundai 원격 신호.
  - 신호 타이밍(펄스 폭, 스트로브 후 응답 시간)을 실제 매뉴얼 값에 맞춤.
- **완료 기준**: KUKA Automatic External 시퀀스(서보 → `$EXT_START` → PGNO 선택 → 실행 → 완료)를 Modbus 로만 끝까지 구동하는 예제 PLC 시퀀스 + 테스트.

#### P0-3. 안전 신호와 정지 범주 — M ✅ 1단계 완료

- **내용**
  - 비상정지(E-Stop) 입력·UI 버튼: 즉시 정지 + 서보 OFF(Stop 0) + 알람, 해제 후 리셋 필요.
  - 안전 펜스(도어) 입력: 자동 운전 중 열리면 Stop 1(감속 정지 후 서보 OFF) 또는 Stop 2(홀드) — 설정 선택.
  - 인에이블 스위치(TEACH 모드에서만 이동 허용) — 조그 연동.
  - 상태 출력: 비상정지 중, 펜스 열림, 안전 회로 정상.
- **완료 기준**: 비상정지 → 해제 → 알람 리셋 → 서보 ON → 재시작 복귀 시퀀스가 상태 비트·OPC UA·제조사 프로토콜에 일관되게 반영.

#### P0-4. 통신 트래픽 모니터 — M

- **내용**
  - `통신` 탭에 인터페이스별 **접속 클라이언트 목록**(IP:포트, 접속 시각, 요청 수, 오류 수).
  - 요청/응답 원문 기록: 텍스트 프로토콜은 그대로, 바이너리(HSE, VarProxy, Modbus)는 **헥스 덤프 + 해석**(예: `FC03 addr=0 qty=10 → [..]`).
  - 필터(인터페이스·클라이언트·오류만), 일시정지, 파일로 내보내기.
  - 잘못된 요청은 거부 이유를 명시 (예: "Modbus 예외 02 — 주소 120 은 예약 영역").
- **완료 기준**: 메시지 억제 없이 초당 수백 건을 기록해도 UI 가 끊기지 않음(링 버퍼), 7개 인터페이스 모두 해석 표시.

#### P0-5. 프로토콜 적합성 검증과 공개 — M (실제 장비 접근 필요)

- **내용**
  - 실제 컨트롤러(또는 제조사 공식 시뮬레이터: RobotStudio 가상 컨트롤러, KUKA OfficeLite, MotoSim EG-VRC 등)와 같은 요청을 보내 응답을 캡처.
  - 캡처를 **골든 패킷 테스트**로 저장해 회귀 방지.
  - 인터페이스별 **검증 매트릭스**(명령·검증 방법·결과·차이점)를 문서로 공개.
- **완료 기준**: 인터페이스별 지원 명령의 검증 상태가 `실기 검증 / 매뉴얼 기준 / 추정` 으로 표시되고, `추정` 항목이 0 이 되거나 명시적으로 경고됨.

### P1 — 시험 효율 (예외 처리와 회귀 시험)

#### P1-1. 고장 주입 패널 — M

- 통신: 응답 지연(ms), 패킷 손실(%), 특정 인터페이스 연결 강제 종료, 응답 없음.
- 로봇: 지정 알람 발생(제조사 코드), 서보 트립, 모션 중 정지, 도달 불가.
- 주변기기: 그리퍼 파지 실패(확인 DI 미응답), 공작물 없음, 센서 고장(고정 ON/OFF), 컨베이어 정지.
- 시나리오 시험에서 스크립트로도 주입 가능해야 함 (P1-4 연계).

#### P1-2. 제조사별 알람 코드 체계 — S~M

- Yaskawa 4자리 알람 번호, KUKA 메시지 번호, ABB elog 도메인·코드, Kawasaki 오류 코드, Hyundai 알람 번호로 매핑.
- 대표 알람(간섭, 도달 불가, 소프트 리밋, 비상정지, 프로그램 오류) 우선.
- PLC·HMI 의 알람 텍스트 테이블을 실제와 같은 번호로 개발할 수 있게 됨.

#### P1-3. I/O 이름표와 I/O 맵 가져오기 — S ✅ 1단계 완료

- DI/DO 이름·설명 편집, CSV 가져오기/내보내기 (PLC 태그 리스트·I/O 할당표 형식).
- I/O 탭, 신호 타임라인, 트래픽 모니터, 로그에 이름 표시.
- 프로젝트에 저장.

#### P1-4. 시험 시나리오 자동화와 헤드리스 실행 — M

- 시나리오 파일(JSON/YAML): `set DI`, `wait DO (timeout)`, `assert 상태`, `inject fault`, `measure Δt`.
- `node server/index.js --headless --scenario test.yaml` 로 UI 없이 실행, 결과 JUnit XML/HTML 리포트 → CI 에서 PLC 로직 회귀 시험.
- 신호 타임라인 CSV 내보내기, 실행 녹화(상태 로그) 재생.

#### P1-5. 통신 타이밍 모사 — S

- 인터페이스별 처리 주기·응답 지연 설정 (예: RWS 수십 ms, HSE 수 ms), 동시 접속 수 제한(실제 제약과 동일하게).
- 폴링 주기가 너무 빠른 PC 프로그램을 개발 단계에서 걸러낼 수 있음.

### P2 — 범위 확장

#### P2-1. 필드버스 추가 — L

| 필드버스 | 실현 방법 | 비고 |
|---|---|---|
| **EtherNet/IP (CIP) 어댑터** | 순수 JS 로 구현 가능 (TCP 44818 명시 메시지, UDP 2222 암시 I/O) | ABB·Yaskawa·Kawasaki 북미 현장에서 많이 씀. Rockwell PLC 와 바로 연동 |
| **CC-Link IE Field Basic** | 소프트웨어 기반 UDP 프로토콜이라 순수 JS 구현 가능 | 국내 Mitsubishi PLC 현장에 유용 |
| PROFINET · EtherCAT | 원시 이더넷 프레임·실시간 처리 필요 → 순수 JS 불가 | 외부 게이트웨이(Modbus/OPC UA ↔ PROFINET) 사용 가이드 제공 |

I/O 맵은 P0-2 시스템 I/O 프리셋과 같은 할당을 쓰도록 설계.

#### P2-2. 다중 로봇 셀 — L

- 컨트롤러 인스턴스 여러 개, 각자 독립 포트 세트(또는 가상 IP).
- 셀에서 로봇 간 간섭 영역(인터록 존) 신호 → PLC 의 로봇 간 인터록 로직 시험.

#### P2-3. 배포·운영 — S~M

- Docker 이미지, Windows 포터블 패키지(Node 내장 실행 파일), 서비스 등록 방법.
- **폐쇄망 현장용 오프라인 설치 패키지** (npm 접속 없이 설치).
- 버전별 릴리스 노트.

#### P2-4. 접근 제어 — S

- 웹 UI·API 토큰 인증(선택), 읽기 전용 모드, 접속 허용 IP 목록.
- 통신 인터페이스는 실제 컨트롤러처럼 인증 없이 두되, 인터페이스별 켜기/끄기와 허용 IP 로 제한.

#### P2-5. PLC 시뮬레이터 연동 가이드 — S

- 실제 PLC 없이 시험: Siemens PLCSIM Advanced, Mitsubishi GX Simulator3, LS XG5000 시뮬레이터와 에뮬레이터를 연결하는 절차(가능한 통신 경로, 제약)를 문서화.

### 하지 않을 것

- 제조사 공식 시뮬레이터 수준의 정밀 궤적·사이클 타임 보장 (오프라인 프로그래밍 시장은 대상이 아님).
- 제조사 상표·로고·UI 를 복제한 화면.

## 3. 단계별 실행 계획

**진행 현황**: 1단계 구현 완료 — `server/controller.js`(인터록·안전), `server/sysio.js`(시스템 I/O), 검증 `test/interlock.test.js`(KUKA Automatic External 시퀀스를 Modbus 코일만으로 끝까지 구동). 사용법은 [매뉴얼 9.1~9.3절](MANUAL.md#91-io-이름표).
남은 제약: 인터록 규칙은 제조사 공통 단순화 모델, 시스템 I/O 프리셋 이름·논리는 근사치(P0-5 적합성 검증에서 실제 매뉴얼·장비와 대조 필요), TEACH 감속·감시 정지는 미구현.


| 단계 | 기간(1인 기준) | 항목 | 결과물 |
|---|---|---|---|
| 1단계: 현실성 | 약 6~8주 | P0-1 모드 인터록, P0-2 시스템 I/O, P0-3 안전 신호, P1-3 I/O 이름표 | "실제 로봇과 같은 시퀀스로 PLC 를 개발할 수 있다" |
| 2단계: 디버깅·자동화 | 약 6~8주 | P0-4 트래픽 모니터, P1-1 고장 주입, P1-2 알람 코드, P1-4 시나리오 자동화, P1-5 타이밍 | "예외 처리까지 자동으로 회귀 시험할 수 있다" |
| 3단계: 신뢰·확장 | 장비 확보에 따라 | P0-5 적합성 검증, P2-1 EtherNet/IP·CC-Link IE Field Basic, P2-3 배포 | "검증된 범위가 공개되어 있고, 현장 PLC 와 바로 붙는다" |
| 이후 | | P2-2 다중 로봇, P2-4 접근 제어, P2-5 PLC 시뮬레이터 가이드 | |

P0-5(적합성 검증)는 실제 컨트롤러나 제조사 시뮬레이터 접근이 필요하므로, 1단계와 병행해 장비 확보부터 시작하는 것을 권합니다.

## 4. 성공 지표

- 파일럿 SI 업체에서 에뮬레이터로 개발한 PLC 프로그램을 실제 로봇에 적용할 때 **통신·핸드셰이크 관련 수정 건수**.
- 로봇 입고 전 PLC 프로그램 완성도(현장 시운전 기간 단축 일수).
- 인터페이스별 검증 매트릭스의 `실기 검증` 비율.
